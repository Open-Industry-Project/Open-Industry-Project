### jolt-physics is a local fork, not the upstream package

`jolt-physics` does not come from npm here. It is a local build, version
**`1.1.0-oip.9`**, installed from `vendor/jolt-physics-1.1.0-oip.9.tgz` through a
`file:` dependency in `package.json`. No such version is published on npm.

The vendored `package.json` names the version and the fork in its `description`, but
keeps upstream's `repository` and `homepage` fields. Those point at
<https://github.com/jrouwe/JoltPhysics.js>, which has no `1.1.0-oip.9` and none of the
changes listed here.

**The fork's source is in this repository:** upstream's `1.1.0` tag plus the four patches
in `vendor/jolt-physics-src/`, which `node scripts/jolt-src.mjs <dir>` applies to a fresh
upstream clone.

- **Upstream:** JoltPhysics.js by Jorrit Rouwe (MIT), a WASM build of Jolt Physics.
- **License:** unchanged. The MIT text travels with the binary inside the tarball at
  `package/LICENSE`, and is also tracked at `vendor/jolt-physics/LICENSE`.
- **What diverges:** the build exposes a native `ConveyorContactListener` to
  JavaScript, so a conveyor's surface velocity is applied in the physics step rather
  than from JS. The engine keeps a JS implementation of the same behaviour and picks
  between them at runtime (`src/sim/worker.ts`, `src/sim/world.ts`). The live one is
  reported as `conveyorListener: 'native' | 'js' | 'none'`, and `?jsconveyor` forces
  the JS path. So the fork is detectable, and the app runs without it.
- **What the four commits touch**, against upstream's `1.1.0` tag (523 insertions in
  6 files):
  `JoltJS.h` (+315, the listener and `BodySnapshot`, a batched reader for body positions
  and rotations), `JoltJS.idl` (+20, the bindings that expose them to JavaScript),
  `CMakeLists.txt` (+15/-2: sizes the thread pool to the machine, fixes a node worker
  import, applies the patch), and a `patches/` directory that applies a
  coupled-planar-friction patch to the Jolt C++ source the build pulls in. The shipped
  single-threaded builds are also compiled with SIMD, a build option rather than a source
  change (`vendor/README.md`).
- **Rebuilding:** see [vendor/README.md](vendor/README.md). The `patches/README.md` that
  the first patch adds explains the friction patch.
- **Traceability:** the `-oip.N` suffix is applied when the tarball is packaged, and
  the fork's own `package.json` reads `1.1.0`. So `-oip.9` does not name a commit of
  the fork.

Only the built tarball lives here. MIT requires the copyright notice to travel with it,
which it does. MIT does not require publishing the modifications, and they are
published anyway so anyone can rebuild the binary.

## Development-time tooling: the GPL boundary

The Open Industry Project is MIT. Some of the tools it is tested against are GPL-3.0. A lint rule keeps
the two apart.

**The rule: GPL code is a development-time oracle only. It is never shipped, never committed, and never
imported by `src/`.** The ST engine, the Modbus TCP server and the external-PLC link are this project's
own work. Nothing under `src/`, and so nothing in `dist/` or the desktop app, contains or links GPL code.
These tools check our work: they compile our exported programs and run them, to test that a program
behaves the same on a real PLC as in the simulator.

`eslint.config.js` (`gplOracleBan`) refuses an import of `scripts/**`, `.oracle-openplc/**` or `strucpp`
from anywhere in `src/**`. One such import inside the app would make the shipped binary a combined work
under the GPL, and nothing in the importing file would show it.

| Component | License | How it is used |
|---|---|---|
| [openplc-editor](https://github.com/Autonomy-Logic/openplc-editor) (Autonomy Logic) | GPL-3.0 | Fetched at a **pinned SHA** into `.oracle-openplc/` (gitignored) by `scripts/lib/openplc-editor.mjs`, and run **in scripts** to build our exported program the way the real editor does: `npm run st-oracle:openplc`, `npm run openplc-loop`. |
| [STruC++](https://www.npmjs.com/package/strucpp) | GPL-3.0-or-later | The editor's ST compiler, installed as a dependency **of the fetched editor** inside the same gitignored work dir. |
| OpenPLC Runtime v4 | GPL-3.0 | Run as a **separate program** (a local install, or the upstream container in CI) which `npm run openplc-loop` drives over its REST API and Modbus TCP. Never linked, never redistributed. |
| MATIEC, PLCopen TC6 schema | their own terms | The IEC conformance oracles (`npm run st-oracle`, `:xml`). Fetched and run the same way, never shipped. |
| ffmpeg-static | GPL | Build-only devDependency; nothing it produces is linked into the bundle. |
| [snap7](https://snap7.sourceforge.net/) (through [python-snap7](https://github.com/gijzelaerr/python-snap7) 2.x) | LGPL-3.0 (python-snap7: MIT) | Installed by hand into `.s7-loop/` (gitignored) and run as a **separate S7 server process** by `npm run s7-loop`. Never linked, never redistributed. |
| libplctag's `ab_server` | MPL-2.0 OR LGPL-2.0-or-later | The upstream release's EtherNet/IP test simulator, fetched beside the library by `scripts/fetch-libplctag.mjs` and run as a **separate process** by the EtherNet/IP tests. electron-builder leaves it out of the installer. |

Running a GPL program is unrestricted, and a GPL compiler's license does not reach what it compiles, so our
exported ST stays ours.

**CI artifacts.** The `openplc-loop` job uploads `.oracle-openplc/loop/`, and `program.zip` inside it is
assembled by the GPL editor and contains STruC++ runtime headers. A public repo's downloadable artifacts are
distribution, so the job writes a
`THIRD-PARTY-NOTICE.txt` beside the bundle naming both licenses and the pinned SHA that is their
corresponding source.

## Development-time tooling: no commercial vendor software

No commercial vendor software (a vendor's IDE, PLC runtime or SCADA) is used to develop or test this
project. Its external checks are open source: MATIEC, STruC++, the OpenPLC editor and runtime, the
PLCopen TC6 schema, snap7 (an S7 server, for `npm run s7-loop`) and libplctag's `ab_server` (an
EtherNet/IP test simulator). Nothing a vendor's software produced is committed or shipped.

The one vendor component the app itself uses is Beckhoff's `TcAdsDll.dll`, for the ADS link, and it is
loaded at run time from the TwinCAT installation already on the user's PC, under that user's license (see
the ADS note above, and [src/plc/DEVICE-IO.md](src/plc/DEVICE-IO.md)). The app's connections to a
vendor's controller or SCADA reach the user's own system, under the user's own license.
