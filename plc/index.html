PLC language reference

The simulator's built-in PLC runs IEC 61131-3 Structured Text and Ladder Diagram. Ladder is a second way to write the same programs: each rung is translated to the Structured Text that means it, so both run on one engine.

This page lists what the engine accepts, what it refuses, where it differs from the standard, and which outside tools check it. It is generated from the engine. Every example below was compiled while the page was built, and every refusal shows the message the compiler gave.

Within the subset, a program is meant to behave the way a real IEC runtime would, so code written here carries over to a physical PLC; where it knowingly behaves differently, the difference is listed. There is no compliance statement and no PLCopen certification.

1. What is and is not claimed

Claimed

  • Within the subset, a program behaves the way a real IEC runtime would, scan for scan. For ladder, where IEC leaves a choice open, this page states the engine's own rule (section 3).
  • A program can leave the simulator as a spec-legal .st file, or as PLCopen TC6 XML, the IEC exchange format, with ladder as an LD body.
  • Anything the engine does not accept is refused by name, with the conversion or substitute to write.
  • The deliberate differences we know of are listed in section 7.

Not claimed

  • Compliance. There is no statement against the standard's feature tables and no PLCopen certification.
  • Completeness. Event tasks, 64-bit types, WSTRING and the other gaps in section 4 are missing.
  • Function Block Diagram, Sequential Function Chart and Instruction List. Only Structured Text and Ladder Diagram are read.
  • Vendor extensions. IEC text is read as written, and vendor extensions are not translated.
  • All of 3rd-edition object orientation: function blocks take METHOD, EXTENDS and INTERFACE, and variables take REF_TO, but there is no CLASS or NAMESPACE.

Control flow

IF / ELSIF / ELSE
VAR_INPUT n : INT; END_VAR VAR_OUTPUT q : INT; END_VAR
IF n > 10 THEN q := 2; ELSIF n > 0 THEN q := 1; ELSE q := 0; END_IF;
CASE with lists and lo..hi ranges
VAR_INPUT n : INT; END_VAR VAR_OUTPUT q : INT; END_VAR
CASE n OF
  1, 3: q := 1;
  4..9: q := 2;
  -1: q := 9;
ELSE q := 0;
END_CASE;
FOR with BY
VAR i : INT; sum : INT; END_VAR
FOR i := 10 TO 0 BY -2 DO sum := sum + i; END_FOR;
WHILE and REPEAT ... UNTIL
VAR i : INT; j : INT; END_VAR
WHILE i < 5 DO i := i + 1; END_WHILE;
REPEAT j := j + 1; UNTIL j >= 5 END_REPEAT;
EXIT, CONTINUE, RETURN
VAR i : INT; n : INT; END_VAR
FOR i := 1 TO 10 DO
  IF i = 3 THEN CONTINUE; END_IF;
  IF i = 8 THEN EXIT; END_IF;
  n := n + 1;
END_FOR;
RETURN;

Whole structs and arrays assign as values

VAR_GLOBAL t : TON; END_VAR

TYPE Inner : STRUCT a : INT; END_STRUCT; END_TYPE

VAR p : Outer; n : INT; END_VAR

Multi-dimensional ARRAY with a repeated initialiser
VAR grid : ARRAY [1..2, 0..3] OF INT := [1, 2, 6(0)]; n : INT; END_VAR
n := grid[2, 1];
Enumerations are their own type
TYPE Mode : (Idle, Running := 10, Fault); END_TYPE
VAR m : Mode := Running; n : INT; END_VAR
CASE m OF
  Idle: n := 0;
  Running: n := 1;
  Fault: n := 2;
END_CASE;
Subranges, enforced on every store
TYPE Percent : INT (0..100); END_TYPE
VAR p : Percent := 50; END_VAR
p := 60;
VAR_EXTERNAL, checked against the VAR_GLOBAL it names
VAR_GLOBAL Shared : INT; END_VAR
VAR_EXTERNAL Shared : INT; END_VAR
Shared := 1;
Located variables at inputs and outputs (AT %IX0.0, AT %QW4)
VAR
  Eye AT %IX100.0 : BOOL;
  Run AT %QX100.0 : BOOL;
  Count AT %IW2 : INT;
END_VAR
Run := NOT Eye;

The address is how the variable meets the world: a scene part whose PLC tag is %IX100.0 feeds it, and an external controller reaches it at that address. Declared in VAR (or VAR_GLOBAL), one variable per address, and the type has to fit the size (a bit holds BOOL, a word INT, UINT or WORD). A function block or function cannot locate a variable.

Located variables in memory (AT %MW0, %MD1, %MX8.0)
VAR
  Count AT %MW0 : INT;
  Total AT %MD1 : DINT;
  Flag AT %MX8.0 : BOOL;
END_VAR
Count := Count + 1;
Flag := Count > 3;

Storage the program keeps, read and written by name: OpenPLC keeps a SCADA’s values at %MW and %MD, so its programs carry these. No scene part binds a memory address; the OPC UA server publishes the variable by name.

Library

The PLCopen motion blocks on an AXIS_REF (MC_Power, MC_MoveAbsolute, MC_MoveVelocity, MC_Halt, MC_Stop, MC_Home, ...)
VAR Ax : AXIS_REF; pwr : MC_Power; mv : MC_MoveAbsolute; END_VAR
pwr(Axis := Ax, Enable := TRUE);
mv(Axis := Ax, Execute := pwr.Status, Position := 10, Velocity := 20, Acceleration := 100, Deceleration := 100);

A subset of the PLCopen Function Blocks for Motion Control (version 2.0, single axis; not certified), with this engine's choices where PLCopen leaves one written down in docs/motion-control.md: trapezoidal moves (a block's Jerk input is accepted and ignored), an abort, BufferMode Buffered (a queue of moves), the Busy / Done / Active / CommandAborted / Error handshake, software limits. On a real controller the blocks come from its own PLCopen motion library, so an export writes the calls and not the blocks; the Blending buffer modes (a block given one raises Error), gearing, cams and axis groups are not here.

A standard function called with IEC’s parameter names (LIMIT(MN := 0, IN := x, MX := 10))
VAR x : INT := 50; n : INT; s : STRING := 'conveyor'; t : STRING; END_VAR
n := LIMIT(MN := 0, IN := x, MX := 10);
t := MID(IN := s, L := 3, P := 2);
** exponentiation (EXPT)
VAR a : REAL; END_VAR
a := 2.0 ** 10.0;
The time and date functions (ADD_TIME, SUB_DT_DT, CONCAT_DATE_TOD, ...)
VAR a : TIME := T#1s; b : TIME; t : TOD := TOD#12:00:00; END_VAR

Signed, unsigned and bit-string families, kept apart
VAR

REAL (single precision) and LREAL

Tasks and programs

A PROGRAM ... END_PROGRAM, which with no CONFIGURATION runs on the scan time
PROGRAM Main
VAR n : INT; END_VAR
n := 1;
END_PROGRAM
CONFIGURATION / RESOURCE / TASK, each task on its own INTERVAL
PROGRAM Main
VAR n : INT; END_VAR
n := n + 1;
END_PROGRAM

CONFIGURATION Cfg
  RESOURCE Res ON PLC
    TASK Fast(INTERVAL := T#10ms, PRIORITY := 1);
    TASK Slow(INTERVAL := T#100ms, PRIORITY := 2);
    PROGRAM A WITH Fast : Main;
    PROGRAM B WITH Slow : Main;
  END_RESOURCE
END_CONFIGURATION

Tasks run on SIM time: each comes due when its INTERVAL elapses, and tasks due together run by PRIORITY (0 first). A scan takes no sim time, so no task interrupts another. An instance variable is addressed as Instance.Name in the watch table and by scene tags.

A PROGRAM instance with no task, which runs continuously
PROGRAM Main
VAR n : INT; END_VAR
n := n + 1;
END_PROGRAM

CONFIGURATION Cfg
  RESOURCE Res ON PLC
    TASK Fast(INTERVAL := T#10ms, PRIORITY := 1);
    PROGRAM A WITH Fast : Main;
    PROGRAM Always : Main;
  END_RESOURCE
END_CONFIGURATION

IEC gives a program with no task the lowest priority and re-runs it as soon as it finishes; on a sim clock that is once per physics step, after that step's periodic scans.

Code outside every POU beside a CONFIGURATION, run by an instance that names no type
VAR n : INT; END_VAR
n := n + 1;

CONFIGURATION Cfg
  RESOURCE Res ON PLC
    TASK Fast(INTERVAL := T#10ms, PRIORITY := 1);
    PROGRAM Main WITH Fast;
  END_RESOURCE
END_CONFIGURATION

An extension: the variables are the program's top-level variables, seen by every POU under their bare names, and the statements run from the program instance with no type. Export writes that code as a PROGRAM of its own.

Object orientation

METHOD on a function block: a result, outputs, in-outs, temporaries that start over each call
FUNCTION_BLOCK Acc
VAR n : INT; END_VAR
METHOD Put : INT
  VAR_INPUT v : INT; END_VAR
  n := n + v;
  Put := n;
END_METHOD
END_FUNCTION_BLOCK

VAR a : Acc; r1 : INT; END_VAR
r1 := a.Put(v := 3) + a.Put(4);
EXTENDS, overrides, SUPER^.M() and SUPER^(), ABSTRACT, FINAL, OVERRIDE
FUNCTION_BLOCK ABSTRACT Shape
METHOD ABSTRACT Area : REAL
END_METHOD
METHOD Twice : REAL
  Twice := 2.0 * Area();
END_METHOD
END_FUNCTION_BLOCK

FUNCTION_BLOCK Square EXTENDS Shape
VAR_INPUT side : REAL; END_VAR
METHOD OVERRIDE Area : REAL
  Area := side * side;
END_METHOD
END_FUNCTION_BLOCK

VAR sq : Square; a : REAL; END_VAR
sq(side := 3.0);
a := sq.Twice();

A method called on THIS (THIS.M(), or by its bare name) runs the override of the instance's own class. A derived block runs its own body, not its base's, unless it calls SUPER^(). IEC writes THIS with no ^ and SUPER with one; THIS^ is refused by name.

INTERFACE, IMPLEMENTS, and variables of an interface type
INTERFACE IDrive
  METHOD Travel : INT
    VAR_INPUT dist : INT; END_VAR
  END_METHOD
END_INTERFACE

FUNCTION_BLOCK Belt IMPLEMENTS IDrive
VAR p : INT; END_VAR
METHOD Travel : INT
  VAR_INPUT dist : INT; END_VAR
  p := p + dist;
  Travel := p;
END_METHOD
END_FUNCTION_BLOCK

VAR belt : Belt; d : IDrive; x : INT; END_VAR
d := belt;
IF d <> NULL THEN x := d.Travel(dist := 2); END_IF;

An interface variable that refers to no instance is NULL (compared with NULL, or 0); a call through it faults the scan. STruC++ 0.6.2, OpenPLC's compiler, has no interface variables yet, so a program that uses them does not build for OpenPLC.

REF_TO, REF(), ^ and NULL: IEC references
TYPE Pkg : STRUCT id : INT; END_STRUCT; END_TYPE
VAR zones : ARRAY [1..3] OF Pkg; z : REF_TO Pkg; z2 : REF_TO Pkg; ok : BOOL; END_VAR
z := REF(zones[2]);
z^.id := 9;
z2 := z;
ok := z2 <> NULL;

A reference is a variable of a POU (or a block's or method's input, given by the call), never a struct field or an array element here. It is given REF(place), another REF_TO or NULL, compared with NULL, and dereferenced with ^; dereferencing one that is NULL faults the scan.

A METHOD returning a whole structure or named array
TYPE Pkg : STRUCT id : INT; END_STRUCT; END_TYPE
FUNCTION_BLOCK Sorter
METHOD Make : Pkg
  VAR_INPUT id : INT; END_VAR
  Make.id := id;
END_METHOD
END_FUNCTION_BLOCK

VAR s1 : Sorter; box : Pkg; END_VAR
box := s1.Make(id := 7);
An ARRAY OF an interface, each element pointed at an instance
INTERFACE IDrive
  METHOD Travel : INT
    VAR_INPUT dist : INT; END_VAR
  END_METHOD
END_INTERFACE

VAR drives : ARRAY [1..4] OF IDrive; i : INT; x : INT; END_VAR
FOR i := 1 TO 4 DO
  IF drives[i] <> NULL THEN x := x + drives[i].Travel(dist := 1); END_IF;
END_FOR;

Tolerated input forms, exported in IEC form

An enumeration in a declaration: m : (Idle, Run, Stop)
VAR m : (Idle, Run, Stop) := Run; n : INT; END_VAR
IF m = Run THEN n := 1; END_IF;

IEC. It is an enumeration of the variable's own, its members named bare; PLCopen carries it as the variable's type. MATIEC parses it but cannot generate it ("C code generator does not currently support anonymous enumerated data types").

A STRUCT field with a default value
TYPE Axis :
STRUCT
  Speed : REAL := 1.5;
  Mode : INT := 2;
END_STRUCT
END_TYPE

VAR a : Axis; b : Axis := (Speed := 3.0); s : REAL; END_VAR
s := a.Speed + b.Speed;

IEC. Every value of the type starts there: a variable, a field, an array element, a block's or a function's local; a field a variable's own initializer names takes that value instead. A default is a constant (a literal, an enumeration member, a global CONSTANT). MATIEC refuses a NESTED (field := ...) value of a struct type that has defaults, a gap of its own.

3. Ladder Diagram

The ladder editor draws rungs, and the PLC panel's text view shows the same rungs in a text form. IEC gives ladder no text form, so this one is the project's own. A rung is translated to Structured Text and run by the same engine, so everything in section 2 is available to a ladder program, and the export writes a ladder POU as a PLCopen LD body.

How rungs run

  • A rung runs left to right, each element once, and each element sees what the elements before it wrote. Rungs run top to bottom.
  • IEC leaves the order of a branch's paths open. Paths that hold a contact or a block run first, then paths that hold only coils, each group top to bottom. So a contact on one path of a branch reads a variable as it was before a coil-only path of the same branch writes it.
  • An edge contact passes power for one evaluation after its variable rose or fell. Its memory is updated every evaluation, even while the rung is off, and starts FALSE.
  • A box behind EN is not called while the rung is off. Its outputs hold their values and ENO is off.
  • While a jump's rung is on, the rungs between it and its label are not evaluated, so their coils hold what they last wrote. Jumps go down the section only.

7. Deliberate differences

Each is exercised by a corpus case carrying a divergence note, and reported by the external oracle as known rather than failed.

  1. same-width signed/unsigned ties resolve unsigned, both ordersIEC does not define mixing signed with unsigned at all; our rule is that the UNSIGNED type wins the same-width tie, in either operand order, so the result is deterministic. (Bit strings no longer take part: arithmetic on ANY_BIT is rejected outright, which is what removed the other half of this divergence.)
  2. both operands of a BOOL AND are evaluated, so a guard does not protect a divideThis engine evaluates both operands of a BOOL AND / OR, so the guarded divide faults. IEC leaves operand evaluation open, so implementations may differ: MATIEC stops at a decided operand, so this program returns FALSE there instead of faulting. A program whose behaviour depends on the difference is non-portable whichever way a simulator answers, so this engine answers the way that SURFACES it: a guard that silently worked here would stop a target that evaluates both operands.
  3. FOR evaluates bounds once and owns its iterationThe loop bound is snapshotted at entry here, and BOTH independent IEC compilers whose behaviour could be inspected re-read it every iteration, so this program runs 3 times here and 10 times there. MATIEC: its generated C puts `if (I <= N)` inside the loop, reading the live variable. RuSTy (PLC-lang): its FOR lowering plants the user-written bound expression in the loop's exit test rather than a temporary, and says so in its own comment. Neither is provably right: IEC constrains FOR to a count "determined in advance", but no edition text reachable from here says WHEN the final-value expression is evaluated, so where to read it is this engine's own rule. Two compilers agreeing is weaker evidence than it looks, since both lower FOR to a C/LLVM-style loop where re-reading is the lazy path. The snapshot is kept anyway: it is what makes the iteration count knowable at entry, which is the property FOR exists for (WHILE is the construct for a condition re-tested each pass), and the only runaway guard here is a count rather than a clock (the interpreter faults a loop after 1,000,000 iterations), so a body that grows its own bound would run a million iterations in one scan before that fault stopped it. Because it cannot be settled, it is not left silent either: exporting a loop whose body writes its own bound now WARNS (export.ts), which is the honest response to a difference nobody can adjudicate.
  4. R_TRIG / F_TRIG single-scan pulsesthe literal IEC F_TRIG body fires when CLK starts false; we suppress that startup pulse, since CLK was never TRUE before it
  5. SEL and MUX select; out-of-range MUX yields 0IEC declares an out-of-range MUX selector an error; we return 0
  6. REAL division by zero yields Infinity, not a faultfloat error handling is vendor-defined; REAL division by zero stays IEEE +/-Infinity here, matching PLC float hardware, which flags but does not fault. Only INTEGER division faults the scan
  7. an array index outside its bounds faultsThis engine faults on an array subscript outside its declared range. IEC requires a subscript to be within range but says nothing about what a runtime does when it is not, so faulting is a choice: this engine is where the mistake is cheapest to find. MATIEC does not check: it emits C, which reads past the array and completes the scan, so the replay reports "expected 0 scan lines, got 1" for this case.
  8. a store outside a subrange faultsThis engine faults on a store outside a subrange. IEC declares the range but leaves the runtime free, so faulting is this engine being the place the mistake is cheapest to find, exactly as with an array bound. MATIEC does not check and completes the scan, which is why the replay reports "expected 0 scan lines, got 1" here.
  9. an out-of-range length or position clamps instead of erroringIEC calls an out-of-range length/position an error. This engine clamps to the string instead - faulting a scan over a short string is not behaviour a controller survives.
  10. REAL_TO_STRING formatting is implementation-definedIEC leaves float-to-text formatting to the implementation, and the vendors disagree (trailing zeros, exponent thresholds). We emit the shortest round-trip form. The VALUE is portable; the exact spelling is not, so do not parse it on the target.
  11. TIME_TO_STRING emits an IEC duration literalThe output is an IEC duration literal (T#1s500ms); IEC does not fix a TIME_TO_STRING format. Chosen so the output round-trips back through STRING_TO_TIME.
  12. a fraction of a second prints in milliseconds, and a literal in a STRING reads backIEC fixes no spelling for a calendar value as text. A fraction of a second prints in milliseconds, three places; MATIEC prints six (TOD#07:05:09.500000). Text that is no date reads as 0 (1970-01-01, midnight), as STRING_TO_INT of text that is no number reads as 0.
  13. a TIME_OF_DAY pushed past midnight faults the scanThis engine faults on a TOD result past 24:00:00, the same choice as for an array subscript or a subrange: the simulator is where the mistake is cheapest to find. MATIEC does not check a TOD result: it goes on past 24:00:00 with a value that is no time of day.
  14. a DATE_AND_TIME before 1970 faults the scanThis engine's DT range is a 32-bit unsigned count of seconds from 1970, so it has no earlier instant, and a result before 1970 faults rather than hand a program a value an unsigned count cannot hold. MATIEC's count is signed and would go on.
  15. TIME_TO_DINT counts millisecondsThis engine counts a TIME converted to a number in milliseconds, the unit TIME carries everywhere else. STruC++ (T#1500ms converts to 1500 in 0.6.2) counts the same. MATIEC counts WHOLE SECONDS (T#1500ms is 1), so a program that converts a TIME to a number reads a different number on a MATIEC target such as OpenPLC v3.
  16. DINT_TO_TIME and REAL_TO_TIME read the number as millisecondsMATIEC reads a number converted to a TIME as SECONDS (DINT_TO_TIME(1500) and REAL_TO_TIME(1500.0) are T#1500s), the mirror of its TIME_TO_DINT. This engine reads milliseconds (STruC++ 0.6.2 agrees), so a preset converted from a number lasts 1000 times longer on a MATIEC target such as OpenPLC v3.
  17. faults when a REF_TO that is NULL is dereferencedIEC 61131-3 makes dereferencing a NULL reference an error and leaves what a controller then does to the implementation. This engine faults the scan, naming it, as it faults a subscript out of range; STruC++'s runtime stops the POU the same way (its NullReference fault). MATIEC has no references
  18. faults a method called through an interface that refers to no instanceIEC 61131-3 makes a call through an interface that refers to no instance (NULL) an error and leaves what a controller then does to the implementation. This engine faults the scan, naming it, as it faults a NULL REF_TO dereferenced; a program tests `itf <> NULL` (or `<> 0`) first

9. Import and export

Anything a target may not carry comes back as a warning or a note. A program that quietly means something other than what its author wrote is worse than one that refuses.

Export

  • .st IEC 61131-3 source (.st). Read by MATIEC, STruC++, RuSTy, and any vendor ST editor as paste.
  • .xml PLCopen TC6 interchange XML. Read by IEC 61131-3 tools that import PLCopen XML.
  • The CONFIGURATION, RESOURCE and TASK this simulator does not author are generated on the way out, so one program body can be wrapped for several targets. Beyond that wrapper, Structured Text is written as you wrote it.
  • A ladder POU goes into PLCopen XML as an LD body. In a .st file it is written as the Structured Text it runs as, because IEC gives ladder no text form.
  • A program that does not compile is not exported.

Import

  • A spec-legal .st file. The CONFIGURATION, RESOURCE and PROGRAM wrappers are removed, and the TASK interval becomes the scan time (this page's test file came in at 40 ms).
  • A PLCopen TC6 project, as IEC tools export it. A ladder body comes in as ladder, rung for rung.
  • Anything the subset cannot hold is named in a note, never dropped. An incomplete address such as AT %I*, which only a VAR_CONFIG could complete, comes back with a note asking for the full address. A memory address such as AT %MW0 crosses as written. A rung the engine cannot draw (a bridge, for example), or a body in FBD, SFC or IL, leaves that POU out with a note saying why.

10. Command-line tools

This page and /st-capabilities.json come from the same probe run, so an agent writing a program for this simulator reads the same list a person does. In the repository, these commands check a program without opening the app, and exit non-zero on a failure:

npm run catalogwhat parts exist, their parameters, and the PLC signals each expects
npm run capabilitiesthis manifest: what the engine accepts and refuses, in Structured Text and ladder
npm run check-st -- <path...>an ST file compiles
npm run validate-project -- <path>a project document loads
npm run check-wiring -- <path>every scene tag connects to a program variable
npm run test-project -- <folder>the control logic behaves (JSON tests, real exit codes)
